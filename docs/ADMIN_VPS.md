# hwforai · руководство администратора VPS

Развёртывание закрытой биржи из ветки `maxv` на одном чистом VPS с Ubuntu 24.04 LTS. Схема подходит для одного экземпляра приложения. Подготовьте публичный домен, доступ к репозиторию и почтового провайдера с SMTP. Как начальную конфигурацию для небольшой нагрузки можно взять 2 vCPU, 4 ГБ оперативной памяти и 40 ГБ диска. Пересмотрите ресурсы по объёму вложений, базе и результатам наблюдения.

```text
Браузер → Caddy :443 → приложение :3001 → PostgreSQL 17 в закрытой сети
                            └──────────→ SMTP провайдера с TLS
```

Публичны веб-порты Caddy. У PostgreSQL и приложения нет опубликованных портов. Сценарий рассчитан на выделенный VPS с доверенными администраторами хоста. Межконтейнерное соединение с PostgreSQL на этом VPS использует отдельную закрытую сеть и аутентификацию SCRAM. Для внешней или управляемой базы используйте проверку имени и сертификата через `sslmode=verify-full` и доверенную цепочку CA. Перепроверьте настройку подключения с выбранным провайдером. [Фильтрация трафика Docker](https://docs.docker.com/engine/network/packet-filtering-firewalls/) · [TLS в node-postgres](https://node-postgres.com/features/ssl)

## Порядок работы для человека и ИИ

Перед началом зафиксируйте домен, адрес и назначение VPS, административного пользователя, ожидаемый полный SHA коммита `maxv`, способ доступа к репозиторию, SMTP-порт, адрес владельца площадки, место и политику хранения резервных копий. Для ИИ достаточно этих сведений и ссылок на конфигурационные файлы. Владелец вводит пароли SMTP, начальный пароль и почтовые коды в своей сессии или через менеджер секретов. Приватный SSH-ключ остаётся у владельца. Помощник сообщает статусы команд и ошибки с удалёнными секретами.

Каждый раздел начинается с проверки текущего состояния. При несовпадении цели, занятом порте, обнаруженной рабочей базе, неожиданном изменении Git-ветки, неверном сертификате или неподтверждённой доставке письма остановитесь и разберите конкретную причину. Получите подтверждение владельца перед изменением DNS, правил SSH и межсетевого экрана, переключением работающей версии, восстановлением рабочей базы или удалением данных. После каждого этапа записывайте результат, не копируя конфигурацию с паролями и почтовые коды.

## 1. Подготовка VPS

1. Создайте у провайдера VPS с Ubuntu 24.04 LTS. Добавьте ключ SSH и проверьте в отдельной сессии вход под именным пользователем с `sudo`. Для этой машины оставьте вход по ключу. Правки SSH сперва проверьте через `sudo sshd -t`, затем перезагрузите настройки службы и откройте второй сеанс. Держите доступ к консоли провайдера на случай ошибки. [Ubuntu OpenSSH](https://documentation.ubuntu.com/server/how-to/security/openssh-server/)
2. В панели провайдера разрешите входящий SSH с адресов оператора и TCP 80/443 из интернета. Проверьте, что 5432 и 3001 закрыты. Настройте эти правила также в хостовом брандмауэре, если он используется. Docker управляет своими правилами публикации портов, поэтому для защиты базы оставьте её без `ports` и контролируйте внешний доступ у провайдера. [Docker и брандмауэры](https://docs.docker.com/engine/network/packet-filtering-firewalls/)
3. Направьте DNS-запись A домена на адрес VPS. Добавьте AAAA, только если IPv6 на VPS доступен извне. Сверьте адреса через независимый DNS-резолвер, убедитесь, что 80 и 443 свободны. Caddy выпустит и будет продлевать публичный сертификат. Если домен уже обслуживает другой сайт, согласуйте перенос с владельцем. [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https)
4. Установите Docker Engine из официального APT-репозитория Docker. На чистой Ubuntu выполните шаги для Ubuntu 24.04 из инструкции Docker и установите пакеты `docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin`. Для команд ниже используйте `sudo`. Доступ к Docker даёт полномочия, сопоставимые с root. [Установка Docker Engine на Ubuntu](https://docs.docker.com/engine/install/ubuntu/) · [Права группы docker](https://docs.docker.com/engine/install/linux-postinstall/)

```sh
cat /etc/os-release
sudo apt-get update
sudo apt-get install -y git curl ca-certificates dnsutils openssl
sudo docker version
sudo docker compose version
sudo docker run --rm hello-world
sudo ss -lnt
```

Для шаблона нужен Compose 2.33.1 или новее. В нём поддерживаются `format: raw` для файлов с секретами и `gw_priority`, который задаёт маршрут приложения к SMTP через внешнюю сеть. [Параметры сервисов Compose](https://docs.docker.com/reference/compose-file/services/)

Подтвердите свой домен у почтового провайдера и добавьте его записи SPF, DKIM и DMARC по инструкции провайдера. Разрешите исходящий TCP 587 для STARTTLS либо 465 для TLS с момента подключения. `MAIL_FROM` должен быть адресом `no-reply` на подтверждённом домене. Уточните, разрешает ли провайдер VPS исходящий SMTP. [Nodemailer SMTP](https://nodemailer.com/smtp)

## 2. Получение версии и конфигурации

Клонируйте репозиторий под именным пользователем. Если доступ закрытый, используйте разрешённый владельцем способ аутентификации, например отдельный ключ GitHub с доступом только на чтение. Проверьте, что полученный полный SHA совпадает с согласованным для развёртывания.

```sh
mkdir -p "$HOME/src"
git clone --branch maxv --single-branch https://github.com/kirillpivovarov/hardsales.git "$HOME/src/hwforai-maxv"
cd "$HOME/src/hwforai-maxv"
git remote get-url origin
git status --short
release="$(git rev-parse HEAD)"
git show --no-patch --oneline "$release"
```

После сверки SHA соберите образ. Тег сохраняет связь образа с проверенным исходным кодом.

```sh
sudo docker build --pull -t "hwforai-app:$release" .
sudo docker image inspect "hwforai-app:$release" --format '{{.Id}}'
sudo install -d -m 700 /etc/hwforai /var/backups/hwforai
sudo install -m 644 deploy/compose.vps.yaml deploy/Caddyfile deploy/init-db.sql /etc/hwforai/
```

Шаблоны входят в репозиторий в каталоге `deploy/`. Корневой `compose.yaml` предназначен для локальной демонстрации. В рабочем шаблоне заданы `NODE_ENV=production`, `DEMO_MODE=false`, один доверенный прокси Caddy и постоянный том PostgreSQL. В базе вместо демо-профилей создаётся одна новая учётная запись администратора. [Шаблоны VPS](https://github.com/kirillpivovarov/hardsales/tree/maxv/deploy)

Создайте три файла в `/etc/hwforai` с владельцем root и правами 0600. Пример начального создания файлов на чистом VPS выполните в сессии `sudo -i`. Для уже настроенного экземпляра работайте с действующими файлами и сохраняйте их резервную копию.

```sh
cd /etc/hwforai
set +x
umask 077
db_password="$(openssl rand -hex 32)"
printf 'POSTGRES_PASSWORD=%s\nHWFORAI_DB_PASSWORD=%s\n' \
  "$(openssl rand -hex 32)" "$db_password" > postgres.env
printf 'DATABASE_URL=postgresql://hwforai_app:%s@postgres:5432/hwforai\nOTP_SECRET=%s\n' \
  "$db_password" "$(openssl rand -hex 32)" > app.env
printf 'BOOTSTRAP_ADMIN_PASSWORD=%s\n' "$(openssl rand -hex 32)" >> app.env
unset db_password
```

Создайте `release.env` в той же сессии. Замените значения перед запуском. В `HWFORAI_DOMAIN` указывают имя хоста без протокола и пути. SHA должен совпадать с тегом образа.

```dotenv
HWFORAI_RELEASE=ПОЛНЫЙ_SHA_КОММИТА_MAXV
HWFORAI_DOMAIN=exchange.example.org
ACME_EMAIL=owner@example.org
```

Владелец открывает `app.env` в своём редакторе и дополняет созданные в нём строки. Вместо примеров подставьте параметры владельца и провайдера. Формат `raw` читает значения буквально. Кавычки вокруг значений не нужны. Случайный пароль первого администратора сохраните напрямую в менеджере паролей.

```dotenv
SMTP_HOST=smtp.example.org
SMTP_PORT=587
SMTP_SECURE=false
SMTP_REQUIRE_TLS=true
SMTP_USER=ЗАМЕНИТЬ_НА_ЛОГИН_SMTP
SMTP_PASS=ЗАМЕНИТЬ_НА_ПАРОЛЬ_SMTP
MAIL_FROM=hwforai <no-reply@exchange.example.org>
BOOTSTRAP_ADMIN_USERNAME=site-owner
BOOTSTRAP_ADMIN_EMAIL=owner@example.org
```

При порте 465 укажите `SMTP_PORT=465` и `SMTP_SECURE=true`. При SMTP-релее, где провайдер не требует логина и пароля, уберите обе строки `SMTP_USER` и `SMTP_PASS`. Секрет для одноразовых кодов и CAPTCHA хранится в `OTP_SECRET` и остаётся одинаковым при обновлениях. В `postgres.env` хранятся разные пароли служебного суперпользователя PostgreSQL и прикладной роли. Прикладная роль владеет базой для миграций и работает без прав суперпользователя. Скрипт `init-db.sql` выполняется только на новом томе. Правка `postgres.env` сама по себе не меняет пароли уже созданных ролей.

Выходите из сессии root после записи файлов. Параметры SMTP и начальный пароль не публикуйте в Git, журнале или переписке с ИИ. Доступ к файлам и к `docker inspect` оставьте администраторам VPS.

## 3. Запуск и проверка

Команды выполняются под именным пользователем через `sudo`. Для коротких команд определите функцию в текущей сессии.

```sh
hwcompose() {
  sudo docker compose --env-file /etc/hwforai/release.env \
    -f /etc/hwforai/compose.vps.yaml "$@"
}
hwcompose config --quiet
hwcompose up -d --wait --wait-timeout 180
hwcompose ps
```

Режим `--quiet` проверяет конфигурацию без печати её содержимого. В `ps` база и приложение должны быть `healthy`, Caddy должен работать. Приложение применяет миграции при запуске и проверяет контрольные суммы уже применённых файлов. При ошибке смотрите журнал нужного сервиса. Проверяйте фрагмент перед отправкой в чат.

```sh
hwcompose logs --tail 60 app
hwcompose logs --tail 60 caddy
domain=exchange.example.org
dig +short A "$domain"
curl --fail --silent --show-error "https://$domain/api/v1/health"
curl --silent --show-error --head "http://$domain/"
```

Ожидаются ответ `{"status":"ok"}`, публично доверенный сертификат, переход с HTTP на HTTPS и открытие страницы входа. `domain` замените своим значением. Проверьте доступ с компьютера вне VPS. В Caddy предусмотрен лимит запроса 90 МиБ, чтобы прокси пропускал загрузку десяти снимков допустимого размера. [Caddy request_body](https://caddyserver.com/docs/caddyfile/directives/request_body)

Войдите под начальной учётной записью, дождитесь письма на реальном адресе и введите код на сайте. Действие выполняет владелец. При первом входе приложение потребует сменить реквизиты. Выйдите и заново войдите с новым паролем и новым кодом. Затем удалите из `app.env` все три строки `BOOTSTRAP_ADMIN_…` и пересоздайте только приложение, чтобы они исчезли из окружения контейнера.

```sh
hwcompose up -d --force-recreate --wait --wait-timeout 180 app
curl --fail --silent --show-error "https://$domain/api/v1/health"
```

Вход предыдущего администратора должен по-прежнему работать с новым паролем. Для модераторов заведите отдельные учётные записи под их персональными адресами. Проверьте на одной тестовой учётной записи получение почты и ограничения доступа. При проверке регистрации используйте почтовый адрес, который контролируете, и временный профиль с вымышленными данными.

## 4. Настройка биржи

В **Администрирование → Закрытая биржа → Настройки биржи** проверьте часовой пояс и версию правил. На новой рабочей базе регистрация открыта, дополнительные модули выключены. Перед приглашением участников определите режим работы.

| Задача | Настройка и проверка |
| --- | --- |
| Приглашения | Включите `feature_invites` и выберите `registration_mode=INVITE`. Создайте тестовое приглашение и пройдите вход, анкету и подтверждение правил. |
| Раскрытие и агент | Включите `feature_disclosure_journal` и `feature_representation`. Проверьте согласие двух сторон в чате и подтверждение принципала. |
| Совпадения | Заполните курсы валют и проверьте нужные модели. Включите `feature_matching`, проведите пару тестовых заявок и предложений. |
| Рейтинг | Включите `feature_trust_rating`. Проверьте документы, статусы проверки и поиск с порогом рейтинга. При необходимости установите `disclosure_min_level` после запуска проверки документов. |
| Актуальность | Уточните часовой пояс и почтовые уведомления. При первом включении `feature_actuality` сервис планирует начало в 10:00 по времени биржи и предупреждает участников минимум за 72 часа. Пройдите сценарий продления объявления. |
| Внешний справочник | Включите `feature_catalog_sync` после согласования внешних источников и исходящего доступа. Проверьте состояние задания и очередь предложенных обновлений. |

Откройте рабочую регистрацию после проверки выбранного режима. При закрытом режиме убедитесь, что адрес без кода не позволяет зарегистрироваться. Проверьте доступ гостя и разницу между действиями модератора и администратора. Зафиксируйте дату, SHA, включённые модули и результат проверки без личных данных участников.

## 5. Резервные копии и восстановление

Снимайте резервную копию перед каждым обновлением и по расписанию согласно допустимой потере данных и времени восстановления. Архив включает базу, изображения, документы и переписку. Храните зашифрованную копию вне VPS с ограниченным доступом. Защищённые копии конфигурации и секретов храните отдельно. Том Caddy хранит в том числе ключи сертификатов. При переносе копируйте его только в защищённое хранилище либо перевыпустите сертификат на новом VPS.

Выполните этот пример в Bash. Здесь используется функция `hwcompose` из раздела запуска.

```bash
stamp="$(date -u +%Y%m%dT%H%M%SZ)"
backup="/var/backups/hwforai/hwforai-$stamp.dump"
(
  set -euo pipefail
  hwcompose exec -T -u postgres postgres pg_dump -U postgres -d hwforai --format=custom \
    | sudo sh -c 'umask 077; cat > "$1"' sh "$backup.tmp"
  sudo cat "$backup.tmp" | hwcompose exec -T -u postgres postgres pg_restore --list >/dev/null
  sudo test -s "$backup.tmp"
  sudo mv "$backup.tmp" "$backup"
  sudo sha256sum "$backup"
)
```

Перенесите копию и контрольную сумму в защищённое хранилище. Тест восстановления состоит в загрузке копии в новую пустую БД с отдельным именем и проверке данных. [Резервное копирование PostgreSQL 17](https://www.postgresql.org/docs/17/backup-dump.html) · [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)

```sh
recovery_db="hwforai_verify_$(date -u +%Y%m%d%H%M%S)"
hwcompose exec -T -u postgres postgres createdb -U postgres -O hwforai_app -T template0 "$recovery_db"
sudo cat "$backup" | hwcompose exec -T -u postgres postgres pg_restore \
  -U postgres -d "$recovery_db" --no-owner --role=hwforai_app \
  --exit-on-error --single-transaction
hwcompose exec -T -u postgres postgres psql -X -U postgres -d "$recovery_db" \
  -v ON_ERROR_STOP=1 -c "SELECT count(*) AS migrations FROM schema_migrations;
  SELECT role, count(*) FROM users GROUP BY role;
  SELECT count(*) AS listings FROM listings;"
```

Сверьте ключевые записи по идентификаторам без выгрузки контактов. Для полного прогона запускайте отдельный проверочный экземпляр без исходящих писем реальным получателям. Для восстановления после аварии сначала создайте чистый VPS и роли базы по шаблону, затем восстановите архив. Уточните SHA приложения, соответствующий архиву. Переключать рабочий `DATABASE_URL` на восстановленную базу можно после проверки и подтверждения владельца. Действующую базу оставляйте в сохранности до завершения проверки.

## 6. Обновление и откат

1. Получите согласованный SHA нового релиза. Под именным пользователем выполните `git fetch origin maxv`, сверьте `git rev-parse origin/maxv` и сравните изменения с установленным SHA, особенно `server/migrations` и `deploy`. Перейдите на новый SHA через `git switch --detach НОВЫЙ_SHA` и соберите образ `sudo docker build --pull -t hwforai-app:НОВЫЙ_SHA .`. Сохраните старый образ и файл с прежними параметрами релиза.
2. Прогоните новый образ на копии базы. Согласуйте окно обновления. Остановите веб-доступ и фоновые задания командой `hwcompose stop caddy app`. Снимите резервную копию базы по разделу 5, проверьте архив. Если требуется изменить файлы из `deploy/`, отдельно сверяйте их перед копированием. Для обычного обновления приложения измените `HWFORAI_RELEASE` в `/etc/hwforai/release.env`. Версию PostgreSQL и имя проекта оставьте прежними.
3. Выполните `hwcompose config --quiet`, затем `hwcompose up -d --wait --wait-timeout 180 app`. Дождитесь здоровья приложения и проверьте журнал миграций, затем откройте доступ через `hwcompose up -d --wait caddy`. Повторите проверки HTTPS, входа, каталога, служебного раздела и почты.
4. Если схема не менялась, откатите `HWFORAI_RELEASE` до прежнего SHA и повторите запуск и проверки. Если миграции применились или совместимость неясна, сохраните текущую базу, восстановите предрелизную копию в отдельную чистую базу и проверьте её прежним образом. При переключении на предрелизную копию изменения, сделанные после её создания, останутся только в более новой базе. Согласуйте действия с владельцем до переключения.

Обновление базовых образов планируйте отдельно. Фиксировать проверенный образ PostgreSQL и Caddy можно через `POSTGRES_IMAGE` и `CADDY_IMAGE` в `release.env`. Обновление основной версии PostgreSQL требует отдельного сценария миграции и проверки резервных копий. Для управления проектом используйте те же файлы, имя и тома.

## 7. Эксплуатация

- Следите извне за HTTPS и `/api/v1/health`, за доступным местом, памятью, временем ответа, очередью писем и возрастом резервной копии. Состояние задач проверяйте в служебном разделе биржи.
- При проблеме с сертификатом сверяйте A и AAAA, TCP 80/443 и время VPS. При ошибке почты проверяйте SMTP-порт, имя хоста, подтверждение домена и настройки TLS. Для проверки используйте собственный адрес, а секреты оставляйте в конфигурации.
- При `Applied migration changed` сравните SHA релиза и применённые миграции. Восстановите правильный исходный файл из того релиза, в котором он был применён. Не переписывайте контрольные суммы в рабочей базе для обхода проверки.
- Периодически проверяйте вход администратора, права модераторов, актуальность SSH-ключей и возможность восстановления. Планируйте обновления Ubuntu и контейнерных образов в согласованные окна.
